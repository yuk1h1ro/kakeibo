### Supabase 無料プランの制約

- **7日間アクセスが無いとプロジェクトが一時停止します。** 復帰はダッシュボードから手動。データは消えませんが、アプリはエラーになり、彼女の共有リンクも見られなくなります
- **自動バックアップがありません。** 操作ミスや事故でデータが消えると戻せません

**（2026-08-05 追記）CSV 書き出し（機能198）を実装しました。** 設定シートから、期間を選んで書き出せます。
BOM 付き UTF-8・15列で、カテゴリ ID や分割の束ねも落としていないので、**あとから人が読んでも表計算で扱っても意味が取れます**。
ホーム画面から起動した PWA では `a[download]` が黙って効かないことがあるため、共有シート経由に切り替わります。

**復元は手作業です**（インポートは利用者が明示的に取りやめた機能199）。月に一度、全期間で取っておくのが現実的だと思います。
これで「消えたら戻せない」状態ではなくなりましたが、**一時停止（下記）はこれでは防げません。**

### セキュリティの残件

- **`<user>.github.io` のオリジン共有** — 同じ GitHub アカウントで第三者のコードを含む Pages を1つでも公開すると、そこから Gemini キー・Discord Webhook URL・Supabase のセッションが読めます。**独自ドメインに移すのが確実**
  - Webhook URL を Supabase(`discord_settings`)にも置くようにしましたが、**この危険は増えていません**。同じオリジンから Supabase のセッションが読めるなら、そもそも RLS 越しに何でも読めるからです。むしろ端末側は localStorage の控えだけになり、ログアウトの後始末で消せるようになりました。Gemini の APIキーは同期していません(撮るのはスマホだけで、鍵を持ち歩く必要がないため)
- **Supabase の `Authentication → URL Configuration` の Redirect URLs** — ワイルドカードや不要なドメインが入っていないか一度確認すること。コード側は自分のオリジンしか送らないので、リスクは Supabase 側の設定にのみ存在する
- **`npm audit` で6件**（vitest / vite / esbuild ほか）— **すべて開発用の依存**で、公開される `dist/` には1バイトも入りません。実際に意味があるのは「`npm run dev` 中に悪意あるサイトを別タブで開くと開発サーバーからソースを読まれうる」1件だけ。vite 5→7、vitest 2→3.2.6 はいずれも破壊的変更を含むので急ぐ必要はない

### 分割保存すると Discord に3通飛ぶ

`¥3,000` を3内訳に分け、3つとも彼女の負担がある場合の実測:

```
🍽️ スーパーA −¥700   残高: ¥19,300(預かり中)
🍽️ スーパーA −¥500   残高: ¥18,800(預かり中)
🍽️ スーパーA −¥250   残高: ¥18,550(預かり中)
```

1内訳だけ負担ありなら1通、負担ゼロなら0通。**表題が3通とも同じ店名で、途中の残高がそれぞれ出る**ため、受け取る側からは「同じ店で3回買い物して残高が3回動いた」ようにしか読めません。

**「1 op = 1通」はこのアプリの一貫した方針で意図的。ただし分割との組み合わせは見落とし**、というのが調査結果です。

- 意図の根拠: `useTransactions.ts` は flush の成功ごとに `buildPartnerOpMessage` を呼び、その関数は op を1件ずつしか受けない形。一括削除・一括編集でも件数分飛ぶ
- 通数を気にした形跡はある: 低下アラートは「またいだ瞬間だけ」という明示的な抑制を持ち、まとめ送信は 2,000 文字単位で束ねている
- 見落としの根拠: `split_group` は同期側・隔離側では明確に意識されている（`quarantine.ts` に「分割は会計まるごと」）のに、**通知側には `split_group` の概念が1箇所も無い**。`splits.ts` の長い設計コメントも通知への波及に一言も触れていない

まとめる場合の懸念: `buildPartnerOpMessage` の「1 op = 1通」という単純さが崩れ、**分割の一部だけ送信に失敗したときの扱い**を決める必要があります。
